Tracing runs database migrations when the API starts. An upgrade can change your database as well as the application, so prepare a recovery point before changing the image.

## Before you upgrade

1. Read the [release notes](https://github.com/Go-Figure-App/tracing/releases) between your current and target versions.
2. Record the current image tag or digest and keep a copy of your Compose file and environment files.
3. Create a [database and file backup](/core/operations/backups), and check that you can restore it.
4. Choose a short maintenance window. Try the new release against a restored copy first when the change is substantial.

Do not change the PostgreSQL major version as part of an ordinary Tracing image update. A database major upgrade needs its own migration procedure. See [Upgrade PostgreSQL 16 to 18](/core/operations/postgresql-18) if you plan to make that change.

## Docker Compose

Check out the reviewed source commit you chose. The included Compose file builds the local image; no Tracing registry image is currently published.

```bash
docker compose build tracing
docker compose up -d tracing
docker compose ps
docker compose logs --tail=100 tracing
```

## Helm upgrades from Kaneo

Keep the Helm release name, namespace, resource names, PVCs and existing credentials. Move application values from `kaneo:` to `tracing:`. A retained PostgreSQL volume already contains its database and role; changing `POSTGRES_DB` or `POSTGRES_USER` does not rename or create them.

For an installation initialized with the old chart defaults, merge these values into your existing values file:

```yaml
nameOverride: kaneo
postgresql:
  auth:
    database: kaneo
    username: kaneo_user
    # Keep the existing password or existingSecret configuration.
```

Use the actual database and role if customized, retain any `fullnameOverride`, and preserve `AUTH_SECRET`. For external PostgreSQL, carry forward the existing connection URI and identity into `tracing.env.database.external`. Render the chart and compare names, selectors, PVCs and credentials with the installed release before applying it. See the [chart upgrade instructions](https://github.com/Go-Figure-App/tracing/blob/main/charts/tracing/README.md#upgrading-an-existing-kaneo-release).

## Mobile device sign-in compatibility

Upgrade the server before distributing the Tracing mobile build. The new app uses the `tracing-mobile` device client ID. Servers predating that default must explicitly include it in `DEVICE_AUTH_CLIENT_IDS`, retaining every CLI/MCP client ID still in use. The current default set is `tracing-cli,tracing-mcp,tracing-mobile,kaneo-cli,kaneo-mcp`. Restart the server after changing the setting; older servers with an unset allowlist can reject the new mobile client.

## Check the result

- Request `/api/health` and confirm the container becomes healthy.
- Sign in, open an existing project, and create a test task.
- Open the same project in another browser session and check a status change appears.
- Upload and reopen an attachment if storage is configured.
- Check email and the integrations your team uses.

Keep the backup until you are satisfied with the result.

## If the upgrade fails

Capture the failing container logs and stop the new application container with `docker compose stop tracing` while you investigate.

Do not assume an old image can read a newly migrated database. Unless the release explicitly supports that downgrade, recover using the previous application image plus its matching database and file backup. Follow [Backups and recovery](/core/operations/backups), and account for any work created since the backup.

Never use `docker compose down -v` as an upgrade or troubleshooting step. It removes the named data volumes.
